# عمليات Nexara

## مراقبة الصحة

يقدم التطبيق مسارين مختلفين للصحة. استخدمهما بصورة منفصلة ولا تفسر liveness على أنه دليل على صحة الخدمات الخارجية.

| المسار | المعنى | الاستخدام الصحيح |
|---|---|---|
| `/api/health/live` | العملية حية ولا ينفذ فحص تبعيات. | إعادة تشغيل العملية إذا أخفق باستمرار. |
| `/api/health/ready` و`/api/health` | يفحص MongoDB والتخزين، ويضيف Supabase في الإنتاج وClamAV عندما يكون مفروضاً. | استخدمه في موازن الحمل وبوابة الإطلاق. |
| `/api/supabase/status` | فحص اتصال خادمي محدود بزمن إلى Supabase Auth. | تشخيص المصادقة، لا كبديل عن اختبار دخول حقيقي. |

إذا أعاد readiness حالة 503 أو `ready: false`، أخرج النسخة من التوزيع ولا توجه مستخدمين جدد إليها. راجع قائمة التبعيات في الاستجابة ثم سجلات التطبيق المنظمة، من دون كشف الأسرار أو تفاصيل بنية البيانات للمستخدمين.

## إجراءات يومية

راجع readiness وسجل أخطاء التطبيق وحالة وظائف الإدخال وسجل التدقيق وحالة النسخ الاحتياطية مرة واحدة على الأقل يومياً. بعد كل نشر، نفذ `npm run production:smoke` من بيئة تشغيل موثوقة مع `NEXARA_DEPLOY_URL` الحقيقي. بعد كل تغيير في أسرار S3 أو Supabase أو MongoDB، نفذ `npm run production:preflight` قبل إعادة إدخال النسخة في التوزيع.

| إشارة تشغيلية | الاستجابة الأولية | قرار الاستمرار |
|---|---|---|
| MongoDB غير جاهزة | أزل النسخة من موازن الحمل، افحص الاتصال والصلاحيات وcluster. | لا تعيدها قبل readiness ناجح. |
| تخزين الكائنات غير جاهز | أوقف رفع الملفات والتنزيلات، وافحص bucket/IAM/endpoint. | لا تقبل ملفات إلى local fallback. |
| Supabase غير جاهز | أبق الواجهة العامة مقيدة، واعتبر الدخول غير مثبت. | لا تعلن نجاح اختبار الحسابات. |
| ClamAV غير جاهز | أوقف قبول الملفات عندما يكون الفحص مفروضاً. | لا تخفف الشرط لتجاوز عطل مؤقت. |
| فشل إدخال كتاب | راجع المرحلة الفاشلة والمصدر والحقوق والملف. | لا تنشر المرشح. |

## السجلات والتنبيه

يكتب الخادم أحداثاً منظمة إلى stdout، ومنها بدء وإيقاف الخادم وأحداث الصحة وإخفاق التبعيات. اجمع stdout في منصة تسجيل موثوقة مع احتفاظ مناسب وتقييد وصول المشغلين. أنشئ تنبيهاً على readiness غير الجاهز، أخطاء MongoDB، فشل التخزين، وفشل قراءة ماسح الملفات. لا تخزن access tokens أو مفاتيح S3 أو محتوى الكتب الكامل في السجلات.

لا يثبت المشروع الحالي نشر منصة مراقبة أو RUM أو تنبيهات خارجية؛ هذه بنية تشغيلية يجب توفيرها في بيئة النشر وتوثيق نجاحها كدليل منفصل.

## إدارة الكتالوج

راقب عدد المرشحين `FAILED` و`READY_FOR_REVIEW` في مسار الإدخال. يجب أن يراجع مدير المحتوى الحقوق والمصدر والإسناد قبل النشر. إذا كشف ملف تالف أو ضار، اعزله خارج مسار الإدخال، وسجل الحادث، واستبدله من مصدر موثوق. لا تعالج المشكلة بإعادة تصنيف الملف أو تعطيل الماسح.

## الحوادث والتصعيد

1. سجّل الوقت والإصدار والبيئة ونقطة الصحة وحالة التبعية؛ لا تسجل أسراراً.
2. حدّد نطاق المستخدمين المتأثرين، ثم أزل النسخ غير الجاهزة من التوزيع.
3. أصلح التبعية أو نفذ rollback للإصدار وفق [دليل النشر](PRODUCTION_DEPLOYMENT.md).
4. نفذ readiness وsmoke بعد الإصلاح، ثم اختبر التدفق المتأثر بحساب حقيقي عند لزومه.
5. دوّن السبب والإجراء الوقائي في سجل الحادث وسجل التدقيق حيث ينطبق.

## حدود rate limiting

يطبق الخادم حد طلبات داخل العملية. هذه الحماية مناسبة كخط أساس لنسخة واحدة، لكنها ليست عداداً موزعاً. في نشر متعدد النسخ، طبق rate limiting موزعاً على الحافة أو بمخزن مركزي قبل إعلان متطلب rate limiting مُثبتاً. اختبر الحدود من IP حقيقي في staging من دون تعطيل الحماية.
